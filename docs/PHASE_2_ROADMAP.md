# Phase 2 Roadmap
### المرحلة الثانية: من الأساس التقني إلى المحتوى والخدمات

**حالة هذه الوثيقة:** تخطيط فقط. لا كود، لا Schema فعلي، لا صفحات. الهدف ترتيب التنفيذ الصحيح وتحديد نطاق كل خطوة قبل الموافقة على البدء الفعلي.

**المرجع الإلزامي لكل ما يلي:** وثيقة `Information Architecture` المعتمدة — كل نموذج بيانات ومسار API أدناه مُشتق منها مباشرة، لا إضافة عليها.

---

## المبدأ الحاكم: لماذا هذا الترتيب تحديدًا

```
1. Database Architecture  →  2. Content Models  →  3. Headless CMS
        ↓                                                  ↓
4. APIs  ←──────────────────────────────────────────────────
   ↓
5. Search
   ↓
6. Admin Dashboard
```

كل مرحلة تعتمد فعليًا على مخرجات التي قبلها:
- لا معنى لتصميم CMS قبل استقرار نماذج البيانات التي سيديرها.
- لا معنى لبناء APIs قبل وجود نماذج بيانات وقواعد مراجعة محتوى واضحة (من سيعتمد المحتوى؟ متى يظهر للعامة؟).
- لا معنى لفهرسة بحث قبل وجود بيانات فعلية ومسار كتابة/تعديل مستقر لها.
- لوحة التحكم آخر خطوة لأنها **عميل استهلاكي** لكل ما سبقها (تستهلك APIs، لا تُعرِّف بيانات جديدة).

---

## 1. Database Architecture (معمارية قاعدة البيانات)

### النطاق
تصميم مخطط Prisma الكامل للمحتوى، مبني فوق نماذج المصادقة الموجودة حاليًا (`User`, `Account`, `Session`) دون تعديلها.

### القرارات المطلوب حسمها قبل أي كتابة Schema
1. **استراتيجية تعدد اللغات للمحتوى**: هل كل نص له صف منفصل لكل لغة (`ContentTranslation` جدول منفصل)، أم حقول JSON متعددة اللغات داخل نفس الصف؟
   - **التوصية الأولية:** جدول ترجمة منفصل (`*Translation`) لكل نوع محتوى رئيسي — يسمح بحالة نشر مستقلة لكل لغة (مقالة قد تُعتمد بالعربية قبل الإنجليزية)، وهو الأنسب لحجم +40 لغة مستهدف.
2. **استراتيجية الإسناد العلمي (Scholarly Attribution)**: كل نص ديني يحتاج ربطًا إلزاميًا بمصدره (رقم آية، رقم حديث ودرجته، مرجع فقهي) — هذا يجب أن يكون على مستوى قيود قاعدة البيانات (NOT NULL + Foreign Keys) لا تحققًا في التطبيق فقط، بما يخدم مبدأ "نظام إسناد إلزامي" في وثيقة IA.
3. **حالات سير عمل المراجعة (Workflow States)**: `DRAFT → PENDING_REVIEW → APPROVED → PUBLISHED → ARCHIVED` كحد أدنى، كحقل `enum` على كل نموذج محتوى، متوافق مع دور `SCHOLAR_REVIEWER` الموجود مسبقًا في `config/permissions.ts`.
4. **الفهرسة**: كل جدول محتوى عالي القراءة (القرآن، الحديث) يحتاج فهارس مركّبة (`locale + slug`, `type + status`) مخطَّطة من اليوم الأول، لا بعد ظهور مشاكل أداء.

### المخرجات المتوقعة من هذه المرحلة
- `prisma/schema.prisma` مُوسَّع (وليس مُعاد بناؤه) بنماذج المحتوى.
- وثيقة قرار (ADR) قصيرة توثّق القرارات الأربعة أعلاه بعد حسمها.

## 2. Content Models (نماذج المحتوى)

### النطاق
تحويل كل قسم في خريطة الموقع (وثيقة IA، القسم 2) إلى نموذج بيانات فعلي. **بالترتيب المقترح حسب الأولوية والاعتمادية:**

| الأولوية | النموذج | يعتمد على | ملاحظة |
|---|---|---|---|
| 1 | `Taxonomy` (الموضوع، المذهب، المستوى، الفئة) | — | يُبنى أولاً لأن كل شيء آخر يُصنَّف عبره |
| 2 | `QuranVerse` / `QuranTranslation` / `QuranTafsir` | Taxonomy | بيانات شبه ثابتة، مرجعية لكل شيء آخر |
| 3 | `Hadith` / `HadithGrading` | Taxonomy | يعتمد على مصادر (كتب/رواة) كنماذج فرعية |
| 4 | `Article` (مقالات عامة، تشمل "عن الإسلام"، الفقه، السيرة) | Taxonomy, ScholarlyReview | نموذج عام مرن يخدم عدة أقسام في IA |
| 5 | `Course` / `Lesson` / `Enrollment` / `Certificate` | Taxonomy, Article/Video | يعتمد على نظام التسجيل (User موجود مسبقًا) |
| 6 | `CommunityPost` / `Event` | Taxonomy | أقل أولوية — يعتمد على وجود مجتمع مستخدمين فعلي أولاً |

### مبدأ التصميم
نموذج `Article` عام ومرن مقصود — لتفادي تكرار نفس البنية (عنوان، محتوى، مؤلف، حالة مراجعة، ترجمات) عبر أقسام "عن الإسلام"، "الفقه"، "السيرة" كنماذج منفصلة. الفروقات بينها تُدار عبر `Taxonomy`، لا عبر جداول Prisma منفصلة — هذا يقلل عدد الجداول ويسهّل البحث الموحّد لاحقًا.

## 3. Headless CMS

### النطاق
ليس بالضرورة منتجًا خارجيًا جاهزًا (Strapi/Sanity) — القرار بين **CMS مبني داخليًا فوق Prisma + Server Actions** (متّسق مع الاختيارات التقنية الحالية) أو **CMS خارجي** يجب أن يُحسم بناءً على معيار واحد: **مدى قدرته على فرض سير عمل المراجعة الشرعية (Scholarly Review Workflow) بدقة**، لأن هذا شرط غير تفاوضي في وثيقة المشروع.

### المتطلبات الوظيفية الأساسية
1. واجهة كتابة/تعديل محتوى (يمكن أن تكون جزءًا من Admin Dashboard في المرحلة 6، لا حاجة لواجهة منفصلة).
2. سير عمل حالة صريح (`DRAFT → PENDING_REVIEW → APPROVED → PUBLISHED`) مع سجل تدقيق (Audit Log) لكل انتقال حالة ولكل تعديل — من عدّل؟ متى؟ ماذا تغيّر بالضبط؟
3. إدارة ترجمات مستقلة الحالة لكل لغة لكل قطعة محتوى (مرتبط بقرار "Database Architecture" أعلاه).
4. صلاحيات محرَّرة بدقة عبر `config/permissions.ts` الموجود مسبقًا — `TEACHER` يُنشئ، `SCHOLAR_REVIEWER` يعتمد، لا تداخل.

### توصية أولية
البدء بـ CMS داخلي بسيط (Server Actions + جداول المراجعة) بدل حل خارجي، لأن المتطلب الأهم (سير المراجعة الشرعية الدقيق) نادرًا ما يدعمه أي CMS جاهز خارج الصندوق دون تخصيص كبير أصلاً — التخصيص الكبير على منتج خارجي غالبًا أعقد من بناء داخلي بسيط فوق بنية موجودة أصلاً (Prisma + RBAC جاهزان).

## 4. APIs

### النطاق
تفعيل بنية `app/api/v1/<resource>/` الموثَّقة مسبقًا (README فقط حاليًا) بموارد فعلية، بالترتيب التالي **بعد** استقرار المرحلتين 1 و2:

1. `GET /api/v1/quran/*` (قراءة فقط أولاً — أبسط نموذج، بلا كتابة، أفضل نقطة بداية)
2. `GET /api/v1/hadith/*`
3. `GET, POST /api/v1/articles/*` (أول مسار يحتاج RBAC فعليًا: `content:create`, `content:publish`)
4. `GET, POST /api/v1/courses/*` + `POST /api/v1/enrollments/*`
5. مسارات المجتمع (أولوية أخيرة، تعتمد على وجود مستخدمين نشطين فعليًا)

### قاعدة صارمة لهذه المرحلة
كل مسار جديد يُبنى مع اختبار (Testing Readiness من Technical Debt يجب أن يُحل **قبل** أول API، لا بعده) واختبار وحدة لأي منطق صلاحيات يستخدمه.

## 5. Search

### النطاق
تفعيل `lib/search.ts` (الواجهة المحايدة الموجودة مسبقًا) بمزوّد فعلي.

### القرار المطلوب حسمه أولاً
OpenSearch مقابل Elasticsearch — معيار الحسم المقترح: الترخيص (OpenSearch أكثر تحررًا) مقابل نضج الأدوات المحيطة (Elasticsearch أوسع انتشارًا). يُوصى بحسمه بمقارنة تقنية قصيرة منفصلة قبل التنفيذ، لا افتراضه ضمنيًا.

### الترتيب الداخلي لهذه المرحلة
1. فهرسة القرآن والحديث أولاً (بيانات شبه ثابتة، فهرسة لمرة واحدة نسبيًا، أفضل نقطة اختبار للبنية).
2. فهرسة تزامنية (Sync) مع دورة حياة `Article`/`Course` (حدث نشر ⇒ إعادة فهرسة) — هذا أول مبرر فعلي لإضافة Background Jobs/Queue من قائمة Technical Debt.
3. واجهة بحث موحّدة عبر `/api/v1/search` تلتف حول `lib/search.ts` دون كشف تفاصيل المزوّد للطبقات الأعلى.

---

## 6. Admin Dashboard

### النطاق
آخر مرحلة بتصميم، لأنها **عميل** لكل ما سبق، لا مصدر بيانات جديد.

### النطاق الوظيفي (مشتق من وثيقة IA، القسم 7)
- إدارة المحتوى متعدد اللغات + قائمة انتظار المراجعة الشرعية (تستهلك CMS من المرحلة 3).
- إدارة المستخدمين والأدوار (تستهلك RBAC الموجود مسبقًا في `config/permissions.ts` — **لا حاجة لإعادة تصميمه**).
- لوحات تحليلات أساسية (استخدام، إتمام دورات) — تحتاج قرارًا لاحقًا حول أداة التحليلات (مبني داخليًا أم مزوّد خارجي).
- إدارة الترجمات ونسب اكتمالها لكل لغة.

### لماذا لا تُبنى أولاً رغم كونها "الواجهة الأكثر وضوحًا"؟
لأن بناءها قبل استقرار نماذج المحتوى وAPIs يعني إعادة بنائها جزئيًا مرتين. الانضباط في الترتيب هنا يوفر وقتًا فعليًا لاحقًا.

## جدول زمني تقريبي (للتخطيط فقط، غير مُلزم)

| المرحلة | المدخل الرئيسي | ملاحظة على المدة |
|---|---|---|
| 1. Database Architecture | وثيقة IA + هذه الوثيقة | الأقصر زمنيًا، لكن الأخطر — يستحق مراجعة علمية وتقنية مشتركة قبل الاعتماد |
| 2. Content Models | مخرجات (1) | يتوازى جزئيًا مع نهاية (1) |
| 3. Headless CMS | مخرجات (1)+(2) | يشمل حسم قرار داخلي/خارجي أولاً |
| 4. APIs | مخرجات (2)+(3) | يبدأ فقط بعد نموذج محتوى واحد كامل (القرآن) لا الجميع دفعة واحدة |
| 5. Search | مخرجات (4) جزئيًا | يبدأ فور استقرار أول مسار GET حقيقي |
| 6. Admin Dashboard | مخرجات (3)+(4) | آخر مرحلة، تستهلك كل ما سبق |

## ما لن يُنفَّذ ضمن هذه المرحلة (تذكير بالنطاق)

هذه وثيقة تخطيط فقط. لا يبدأ أي تنفيذ فعلي (Schema، صفحة، API، مكوّن) إلا بعد موافقة صريحة منفصلة على هذه الخارطة، تمامًا كما جرى الاتفاق عليه في مرحلة الأساس التقني.
