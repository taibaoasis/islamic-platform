# مراجعة هندسية شاملة (Engineering Review)
### المنصة العالمية للتعريف بالإسلام والتعليم الإسلامي — البنية التقنية الأساسية (Foundation)

**تاريخ المراجعة:** يوليو 2026
**نطاق المراجعة:** البنية التقنية الأساسية فقط (Phase 1) — لا يوجد محتوى أو صفحات فعلية بعد.
**ملاحظة منهجية:** التقييمات أدناه تقيس **جاهزية الأساس** الذي بُني، وليس جاهزية "منصة منتَجة بالكامل" — فمعظم الأقسام (SEO الفعلي، Accessibility على مكوّنات حقيقية، Testing) لا يمكن أن تُقيَّم بمعزل عن وجود محتوى وصفحات فعلية لم تُبنَ بعد عمدًا حسب نطاق هذه المرحلة.

---

## 1. Clean Architecture — 8/10

**نقاط القوة:**
- فصل واضح بين الطبقات: `app/` (عرض) ← `services/` (منطق أعمال/صلاحيات) ← `lib/` (بنية تحتية: db, auth, storage, search, redis) ← `config/` (إعدادات مركزية) ← `types/` (عقود).
- `services/auth.service.ts` يفرض حدًا صريحًا: "server-only"، لا يُستورد من مكوّنات العميل.
- بنية `features/` جاهزة لنمط Feature-based Architecture دون إنشاء أي ميزة فعلية قبل الأوان.
- لا توجد أي استدعاءات مباشرة لـ `process.env` خارج `config/env.ts` (مصدر واحد للحقيقة).

**نقاط الضعف:**
- الطبقة لم تُختبر بعد بميزة حقيقية واحدة (Quran/Hadith) — الفصل نظري حتى الآن، وحدود الطبقات الحقيقية ستظهر فقط عند إضافة أول ميزة معقدة (خصوصًا التعامل مع محتوى متعدد اللغات ومراجعة علمية).

**توصيات:**
- عند بناء أول ميزة في Phase 2، وثّق "قالب ميزة" (Feature Template) مرجعي كي تلتزم به بقية الميزات.

---

## 2. Scalability — 7/10

**نقاط القوة:**
- `lib/db.ts`: نمط Singleton لـ Prisma يمنع استنزاف اتصالات قاعدة البيانات.
- طبقات التخزين (`lib/storage.ts`) والبحث (`lib/search.ts`) والتخزين المؤقت (`lib/redis.ts`) مبنية كواجهات مستقلة (abstractions) — استبدال المزوّد لاحقًا (S3 → R2، Redis → مزوّد آخر) لا يمس بقية الكود.
- `next-intl` مع `localePrefix: "always"` يدعم أي عدد من اللغات دون تغيير بنيوي.
- بنية REST مُوثَّقة بنمط `v1/<resource>` قابل لإصدارات مستقبلية (`v2`).

**نقاط الضعف:**
- لا يوجد بعد اختبار حمل (Load Testing) أو تحديد لحدود الأداء الفعلية.
- OpenSearch/Redis غير مفعّلين فعليًا (Technical Debt) — التوسع الحقيقي في البحث والتخزين المؤقت لا يمكن قياسه إلا بعد التفعيل.
- لا توجد استراتيجية Sharding/Partitioning لقاعدة البيانات موثّقة بعد (غير ضرورية في هذه المرحلة، لكن يجب تخطيطها قبل نمو المحتوى).

**توصيات:**
- عند تصميم نماذج المحتوى في Phase 2، خطّط للفهرسة (indexes) والعلاقات مسبقًا بما يخدم قراءة عالية الحجم (100M+ مستخدم يعني قراءة أعلى بكثير من الكتابة).

## 3. Maintainability — 8/10

**نقاط القوة:**
- تعليقات ثنائية اللغة (عربي/إنجليزي) في كل ملف تشرح "لماذا" وليس فقط "ماذا".
- ملفات `README.md` داخل `features/`, `services/`, `app/api/v1/` توثّق الاصطلاح المتّبع قبل وجود أي كود فعلي فيها.
- تسمية موحّدة وقابلة للتنبؤ (انظر قسم Naming Conventions).
- `package.json` نظيف، بدون حزم غير مستخدمة.

**نقاط الضعف:**
- لا يوجد `CONTRIBUTING.md` أو دليل إعداد بيئة تطوير خطوة بخطوة للمطورين الجدد.
- لا يوجد Prettier/format-on-save موحّد مُهيَّأ بعد (الاعتماد حاليًا على ESLint فقط).

**توصيات:**
- إضافة Prettier + `lint-staged` + Husky (pre-commit) في مرحلة لاحقة لضمان اتساق التنسيق قبل أي دمج (merge).

## 4. Security — 7/10

**نقاط القوة:**
- `npm audit`: **0 ثغرات** بعد معالجة 7 ثغرات (تفاصيل في تقرير الإصدار).
- نظام صلاحيات (RBAC) صريح ومركزي — لا منطق صلاحيات متناثر.
- `config/env.ts`: فشل فوري (fail-fast) عند غياب متغيرات بيئة حساسة، بدل فشل صامت لاحقًا.
- فصل `serverEnv` عن `clientEnv` يمنع تسرّب أسرار الخادم إلى الحزمة المرسلة للمتصفح.
- `.env` مستبعد من Git، و`.env.example` لا يحتوي على أي قيمة حقيقية.

**نقاط الضعف:**
- لا توجد رؤوس أمان (Security Headers: CSP, HSTS, X-Frame-Options) مُهيَّأة في `next.config.ts` بعد.
- لا يوجد Rate Limiting على أي مسار (لا حاجة الآن لعدم وجود مسارات فعلية، لكن يجب إضافته قبل تفعيل أي مسار مصادقة حقيقي).
- لا يوجد مزوّد مصادقة فعلي مُفعَّل بعد (Providers فارغة عمدًا) — لا يمكن تقييم تدفق تسجيل الدخول الفعلي أمنيًا حتى يُبنى.

**توصيات:**
- قبل تفعيل أول Provider حقيقي: أضف رؤوس أمان أساسية، وRate Limiting على `/api/auth/*`، وفعّل تتبع محاولات الدخول الفاشلة.

## 5. Performance — 6/10

**نقاط القوة:**
- خطوط مضمَّنة ذاتيًا عبر `next/font` (بدون طلب شبكة عند التشغيل).
- Tailwind v4 (محرك CSS أسرع وحجم إخراج أصغر بنسبة تصل إلى ~70% مقارنة بـ v3).
- Turbopack مفعّل للبناء والتطوير.
- `lib/redis.ts` جاهز كطبقة تخزين مؤقت اختيارية بواجهة بسيطة (`cacheGet`/`cacheSet`).

**نقاط الضعف:**
- لا يوجد محتوى فعلي بعد لقياس الأداء الحقيقي (TTFB، LCP، حجم الحزمة).
- Redis غير مفعّل فعليًا؛ لا استراتيجية تخزين مؤقت مطبَّقة (مجرد بنية جاهزة).
- لا توجد استراتيجية ISR/Static Generation محددة بعد لصفحات المحتوى المستقبلية (القرآن، السنة قابلان للتوليد الساكن الكامل نظرًا لثبات المحتوى).

**توصيات:**
- في Phase 2، صفحات المحتوى الثابت نسبيًا (القرآن، الحديث) مرشّحة قوية لـ Static Generation / ISR بدل العرض الديناميكي الكامل، لتخفيف الحمل بشكل كبير عند 100M+ مستخدم.

## 6. SEO Readiness — 4/10

**نقاط القوة:**
- بنية الروابط متعددة اللغات مع `hreflang` مخطَّطة في وثيقة IA ومطبَّقة بنيويًا عبر `next-intl` (`localePrefix: "always"`).
- `generateMetadata` مفعَّل على مستوى layout مع عنوان ووصف لكل لغة.

**نقاط الضعف:**
- لا يوجد `sitemap.xml` أو `robots.txt` ديناميكيين بعد.
- لا توجد بيانات structured data (JSON-LD) — مهمة جدًا لمحتوى ديني/تعليمي (Article, FAQPage, Course schemas).
- لا توجد صفحات فعلية بعد لتقييم meta tags لكل صفحة (Open Graph, Twitter Cards).
- لا توجد استراتيجية canonical URLs موثّقة تقنيًا بعد (موجودة كمبدأ في وثيقة IA فقط).

**توصيات:**
- هذا البند يجب أن يكون من أوائل ما يُبنى في Phase 2 فور وجود أول نوع محتوى (sitemap ديناميكي + JSON-LD + OG tags) — تأخره مكلف لاحقًا على منصة تستهدف انتشارًا عالميًا عبر البحث.

## 7. Accessibility (WCAG) — 5/10

**نقاط القوة:**
- `dir` و`lang` صحيحان وديناميكيان على `<html>` حسب اللغة (شرط أساسي لقارئات الشاشة العربية).
- الخطوط تدعم النصوص العربية بشكل كامل (IBM Plex Sans Arabic مصمّم لقابلية القراءة).
- مكوّن `Button` يستخدم `<button>` دلاليًا حقيقيًا لا `<div>`.

**نقاط الضعف:**
- لا توجد مكوّنات UI حقيقية كافية بعد لتقييم التباين اللوني (contrast ratio)، حالات التركيز (focus states)، أو دعم لوحة المفاتيح الكامل.
- الأيقونات (`components/icons`) تحتاج فرض `aria-hidden` أو `aria-label` كقاعدة إلزامية عند الاستخدام الفعلي — غير مُختبرة بعد.
- لا يوجد فحص آلي (axe-core / Lighthouse CI) مُدمج في سير العمل.

**توصيات:**
- أضف فحص Accessibility آليًا (axe-core) إلى `npm run lint` أو خط CI منذ أول مكوّن UI حقيقي، لا بعد تراكم المكوّنات.

## 8. Internationalization (i18n) — 8/10

**نقاط القوة:**
- `next-intl` مهيَّأ بالكامل: توجيه، تحميل رسائل، سياق عميل/خادم.
- بنية `locales/{locale}/common.json` واضحة وقابلة للتوسع لأي عدد لغات.
- فصل صريح بين نصوص النظام (المرحلة الحالية) ونصوص المحتوى (Phase 2).

**نقاط الضعف:**
- لغتان فقط مُفعَّلتان حاليًا (ar, en) من أصل +40 مستهدفة في وثيقة المشروع — متوقّع في هذه المرحلة، لكنه يستحق الذكر.
- لا توجد استراتيجية Pluralization/ICU Message Format موثّقة أو مُختبرة بعد لجمل معقدة (next-intl تدعمها لكنها غير مُستخدمة عمليًا بعد).

**توصيات:**
- عند إضافة لغات جديدة، استخدم قائمة تحقق (checklist) موحّدة: الرسائل، الخط، اتجاه الكتابة، تنسيق الأرقام/التاريخ.

## 9. RTL / LTR — 8/10

**نقاط القوة:**
- `getDirection()` مركزية ومشتقة من قائمة `rtlLocales` واحدة — لا قرار RTL متناثر في الكود.
- `@custom-variant dark` وباقي نظام Tailwind v4 لا يتعارضان مع القلب الاتجاهي.
- تنبيه صريح في CSS يذكّر باستخدام خصائص منطقية (`start`/`end`) بدل (`left`/`right`).

**نقاط الضعف:**
- لم يُختبر التبديل RTL/LTR بصريًا بعد على مكوّنات حقيقية (لا توجد مكوّنات كافية).
- لا توجد قاعدة ESLint تلقائية تمنع استخدام `left-`/`right-`/`ml-`/`mr-` في Tailwind (يعتمد حاليًا على انضباط المطور فقط).

**توصيات:**
- أضف قاعدة lint مخصصة أو `eslint-plugin-tailwindcss` مع تحذير على الخصائص الاتجاهية غير المنطقية قبل بدء بناء مكوّنات UI حقيقية.

## 10. Authentication — 6/10

**نقاط القوة:**
- Auth.js (next-auth v4 المستقر) مُهيَّأ بالكامل مع Prisma Adapter الصحيح والمتوافق فعليًا (تم تصحيح خطأ توافق حرج أثناء المراجعة).
- استراتيجية الجلسة (JWT) محددة بوضوح.
- نموذج البيانات (`User`, `Account`, `Session`, `VerificationToken`) قياسي ومتوافق مع Auth.js.

**نقاط الضعف:**
- **صفر Providers مُفعَّلة** — قرار متعمَّد حسب نطاق هذه المرحلة، لكنه يعني أن تسجيل الدخول الفعلي غير مُختبر نهائيًا حتى الآن.
- لا صفحات تسجيل دخول/خروج فعلية (متعمَّد ومطلوب صراحة عدم إنشائها).

**توصيات:**
- Phase 2 (أو مرحلة وسيطة قبلها): فعّل Provider واحد على الأقل (Email أو Google) في بيئة تطوير واختبر التدفق الكامل قبل بناء أي صفحة تعتمد عليه.

## 11. Authorization (RBAC) — 8/10

**نقاط القوة:**
- مصفوفة أدوار/صلاحيات مركزية وحيدة (`config/permissions.ts`) — 7 أدوار مشتقة من فئات الجمهور المستهدف في وثيقة المشروع.
- `hasPermission()` و`requirePermission()` دوال نقية وقابلة للاختبار بسهولة.
- توافق حرفي بين enum الأدوار في Prisma schema وفي `config/permissions.ts` (موثّق صراحة في الكود لمنع الانحراف).

**نقاط الضعف:**
- لم تُستخدم `requirePermission()` بعد في أي مسار API حقيقي (لا توجد مسارات محمية بعد).
- لا يوجد اختبار وحدة (unit test) يثبت صحة مصفوفة الصلاحيات آليًا.

**توصيات:**
- أول ما يُبنى في أي Route Handler محمي مستقبلًا: اختبار وحدة لمصفوفة الصلاحيات نفسها، منفصل عن اختبار الميزة.

**نقاط القوة:**
- مطابقة حرفية لقائمة المجلدات المطلوبة: `app/ components/ features/ lib/ services/ hooks/ types/ prisma/ public/ styles/ config/ locales/ middleware/`.

- لا يوجد أي مجلد فارغ بلا تفسير (README أو .gitkeep مع سبب).

**نقاط الضعف:**
- لا يوجد ملف خريطة (`ARCHITECTURE.md`) واحد يشرح دور كل مجلد في مكان واحد (المعلومات موزّعة حاليًا بين تقارير المحادثة وREADMEs الفرعية).

**توصيات:**
- عند اعتماد Foundation نهائيًا، اجمع خريطة المجلدات في ملف واحد ثابت (يمكن دمجها لاحقًا مع `PROJECT_STATUS.md` أو ملف منفصل).

## 13. Naming Conventions — 9/10

**نقاط القوة:**
- ملفات: `kebab-case` (`theme-provider.tsx`, `use-locale.ts`, `auth.service.ts`).
- مكوّنات React: `PascalCase` (`Button`, `ThemeProvider`, `SessionProvider`).
- دوال ومتغيرات: `camelCase` (`hasPermission`, `getDirection`).
- ثوابت/Enums منطقية: `UPPER_SNAKE_CASE` للقيم الثابتة الحقيقية فقط (`PROTECTED_PATTERNS`)، لا إفراط في استخدامها.
- لاحقات دلالية ثابتة: `.service.ts`, `.action.ts` تُستخدم بانضباط.

**نقاط الضعف:**
- لا يوجد ملف واحد يوثّق هذه القواعد صراحة لمطورين جدد (القواعد مطبَّقة لكنها ضمنية).

**توصيات:**
- أضف قسم "Naming Conventions" مختصر إلى `ARCHITECTURE.md` المقترح أعلاه.

## 14. Type Safety — 8/10

**نقاط القوة:**
- `strict: true` و`noUncheckedIndexedAccess: true` مفعَّلان في `tsconfig.json` (أعلى مستوى صرامة متاح عمليًا).
- Path aliases (`@/*`) موحّدة ومُختبرة عبر Build فعلي ناجح.
- توسيع أنواع Auth.js (`types/next-auth.d.ts`) يجعل `session.user.role` مطبوعًا بدقة في كل الكود بدل `any`.
- `tsc --noEmit`: **صفر أخطاء حقيقية** في كل الكود المُطوَّر — الأخطاء الثلاثة المتبقية سببها الوحيد عدم القدرة على تشغيل `prisma generate` بسبب قيود شبكة بيئة التنفيذ الحالية (انظر Technical Debt)، وليست خطأ في الكود.

**نقاط الضعف:**
- لا يمكن تأكيد نجاح `tsc --noEmit` بنسبة 100% إلا بعد تشغيل `prisma generate` في بيئة حقيقية.

**توصيات:**
- شغّل `npm install && npx tsc --noEmit` فور استلام المشروع للتأكد من الصفر أخطاء فعليًا (متوقَّع بثقة عالية بناءً على تتبّع الأخطاء الثلاثة الحالية إلى مصدر واحد معروف).

## 15. Error Handling — 5/10

**نقاط القوة:**
- `services/auth.service.ts` يرمي أخطاء بأكواد واضحة (`UNAUTHENTICATED`, `FORBIDDEN`) بدل رسائل غامضة.
- `app/api/health/route.ts` يستخدم `try/catch` صريحًا مع استجابة HTTP مناسبة (503).
- `config/env.ts` يفشل مبكرًا وبوضوح بدل ترك الخطأ يظهر لاحقًا في مكان غير متوقع.

**نقاط الضعف:**
- لا يوجد `app/error.tsx` أو `app/[locale]/error.tsx` (حدود خطأ على مستوى React) بعد.
- لا يوجد `app/not-found.tsx` مخصص (يعتمد حاليًا على افتراضي Next.js).
- لا يوجد شكل استجابة خطأ API موحّد مُطبَّق فعليًا (فقط معرَّف كنوع `ApiResponse<T>` في `types/index.ts` دون استخدام حقيقي بعد).

**توصيات:**
- أضف `error.tsx` و`not-found.tsx` على مستوى `app/[locale]/` قبل أي صفحة محتوى حقيقية — هذه ملفات بنيوية (framework-level)، ليست "محتوى" أو "ميزة"، لذا يمكن اعتبارها ضمن استكمال الأساس.

## 16. Logging Strategy — 3/10

**نقاط القوة:**
- `console.error` مستخدم في نقاط حرجة فقط (فشل تحقق env، فشل health check) لا بشكل عشوائي.

**نقاط الضعف:**
- لا يوجد Logger هيكلي (structured logging) — لا مستويات (info/warn/error)، لا معرّف طلب (request id) لتتبّع سلسلة الأحداث.
- لا يوجد تكامل مع أي أداة مراقبة سجلات (Datadog, Better Stack, إلخ).
- هذا أضعف بند في كامل المراجعة.

**توصيات:**
- **أولوية عالية لبداية Phase 2**: أضف مكتبة logging هيكلية خفيفة (مثل `pino`) قبل إضافة أي API حقيقي، لأن غياب السجلات المنظّمة يصعّب تشخيص أي مشكلة إنتاج لاحقًا بشكل كبير.

## 17. Configuration Management — 9/10

**نقاط القوة:**
- `config/env.ts`: مصدر وحيد موثّق ومتحقَّق منه بـ zod لكل متغيرات البيئة (خادم/عميل منفصلان).
- `.env.example` شامل، منظّم بتعليقات، ولا يحتوي على أي سر حقيقي.
- كل الإعدادات (site, themes, fonts, permissions) مفصولة بوضوح حسب مسؤوليتها في `config/`.

**نقاط الضعف:**
- لا يوجد تحقق من التوافق بين بيئات مختلفة (dev/staging/production) بشكل آلي (مثل ملفات `.env.production.example` منفصلة).

**توصيات:**
