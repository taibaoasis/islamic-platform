# SECURITY_BASELINE.md
### Phase 0.1 — Security Baseline

**نطاق هذه الوحدة:** حماية `/admin/**` فقط. لا Prisma، لا Migrations، لا تغيير حزم، لا تغيير UI/CSS/Design System — كما طُلب صراحة.

---

## 1. تدفُّق المصادقة الفعلي (كما هو، لا كما هو مخطَّط)

**الملف:** `lib/auth.ts`

```ts
export const authOptions: NextAuthOptions = {
  adapter: PrismaAdapter(db),
  session: { strategy: "jwt" },
  pages: {},
  providers: [],   // ← فارغة تمامًا
  callbacks: { jwt(...), session(...) },
};
```

### 🔴 اكتشاف حاسم أثناء الفحص (لم يكن موثَّقًا صراحة بهذا الوضوح سابقًا)

**`providers: []` فارغة بالكامل.** لا يوجد Google، لا Credentials، لا Email — **لا توجد طريقة واحدة لأي شخص لتسجيل الدخول فعليًا في المشروع بحالته الحالية.** هذا سابق لهذه الوحدة تمامًا (بُني هكذا في مرحلة التأسيس، موثَّق كتعليق داخل الملف نفسه: "البنية جاهزة فقط... أضف مزوّدي الدخول عند بدء العمل على صفحات تسجيل الدخول الفعلية").

**الأثر المباشر على Phase 0.1:** حراسة `/admin` التي نُفِّذت في هذه الوحدة **تمنع الوصول بشكل صحيح**، لكن **لا يوجد حاليًا أي مستخدم يمكنه اجتياز هذه الحراسة فعليًا** — بما فيه فريق العمل نفسه — حتى يُضاف مزوّد مصادقة حقيقي واحد على الأقل. **هذه ليست مشكلة في تنفيذ Phase 0.1** — هي حالة "فشل آمن" (Fail-Closed) صحيحة ومقصودة: اللوحة كانت مفتوحة للجميع قبل هذه الوحدة، وأصبحت مغلقة أمام الجميع (بما فيهم الإداريون الشرعيون) الآن — وهذا **أفضل بكثير** أمنيًا من البقاء مفتوحة، لكنه يعني أن **إضافة مزوّد مصادقة حقيقي واحد على الأقل** هي الخطوة التالية الحتمية قبل أن يستخدم أي شخص لوحة الإدارة فعليًا — خارج نطاق هذه الوحدة تحديدًا (لم يُطلَب، ولم يُنفَّذ).

### آلية الجلسة
- **الاستراتيجية:** JWT (`session.strategy = "jwt"`) — **بلا حالة (Stateless)**، لا حاجة لاستعلام قاعدة بيانات عند كل فحص جلسة (خلافًا لاستراتيجية Database Sessions).
- **إضافة الدور:** `callbacks.jwt` يضع `user.role` داخل الـtoken عند إنشائه لأول مرة (وقت تسجيل الدخول الفعلي، غير القابل للحدوث حاليًا كما أعلاه)؛ `callbacks.session` ينقل الدور من الـtoken إلى `session.user.role` عند كل قراءة جلسة.
- **التحقق من الأدوار:** يعتمد بالكامل على `config/permissions.ts` (`hasPermission`) — **لا تكرار لمنطق الصلاحيات في أي مكان آخر**، بما في ذلك الإضافات الجديدة في هذه الوحدة.
- **`types/next-auth.d.ts`:** يوسِّع أنواع NextAuth رسميًا (`session.user.role`, `session.user.id`) — موجود مسبقًا وصحيح، لم يُعدَّل.

## 2. تدفُّق التفويض (Authorization) — الجديد في هذه الوحدة

### الأدوات الموجودة مسبقًا (لم تُعدَّل)
```ts
// services/auth.service.ts — كما كانت
getCurrentUser()      // يُعيد المستخدم أو null، لا يرمي أبدًا
requireAuth()         // يرمي Error("UNAUTHENTICATED") إن لم يوجد مستخدم
requirePermission(p)  // يرمي Error("FORBIDDEN") إن نقصت الصلاحية
```
هاتان الدالتان (`requireAuth`/`requirePermission`) **مناسبتان لسياق Server Action** (استثناء يُلتقَط في نقطة الاستدعاء) — **غير مناسبتين مباشرة داخل Layout/Page** (استثناء غير مُلتقَط ⇐ صفحة خطأ 500 عامة، لا إعادة توجيه نظيفة). هذا فرق جوهري تحقَّقنا منه بالفحص، لا افتراضًا.

### الإضافات الجديدة (Phase 0.1، إضافة لا تعديل)
```ts
requireAdminAccess()          // Layer A — البوابة العامة للوحة كاملة
requireAdminPermission(perm)  // حراسة أضيق لأقسام حسّاسة داخل اللوحة
```

**منطق `requireAdminAccess()`:**
1. لا مستخدم (`getCurrentUser()` يُعيد `null`) ⇐ `redirect("/api/auth/signin")` (مسار NextAuth الحقيقي، لا صفحة وهمية).
2. مستخدم موجود لكن بلا أي صلاحية من `ADMIN_BASELINE_PERMISSIONS` (قائمة من 8 صلاحيات: كل شيء عدا `content:read`/`community:post`/`course:enroll` — أي أن VISITOR/MEMBER/STUDENT، الأدوار الثلاثة بلا أي صلاحية تحريرية، تُرفَض هنا) ⇐ `redirect(/${locale})` (الصفحة الرئيسية العامة).
3. غير ذلك ⇐ إعادة كائن المستخدم، السماح بالمتابعة.

**منطق `requireAdminPermission(permission)`:** يستدعي `requireAdminAccess()` أولاً (نفس البوابة العامة)، ثم يتحقق من صلاحية محدَّدة إضافية؛ عدم توفرها ⇐ `redirect(/${locale}/admin)` (رجوع للوحة الرئيسية، لا الصفحة الرئيسية العامة — لأن المستخدم إداري بالفعل، فقط ينقصه صلاحية فرعية).

## 3. المسارات المحمية والعامة

تفصيل كامل في `docs/SECURITY_ROUTE_MATRIX.md`. ملخص:
- **كل مسار تحت `/admin/**`** محمي بالبوابة العامة (`requireAdminAccess`، عبر `admin/layout.tsx`).
- **`/admin/settings/**`** (7 صفحات) محمية إضافيًا بـ`settings:manage` (عبر `admin/settings/layout.tsx`).
- **`/admin/users`, `/admin/users/[userId]`, `/admin/roles`, `/admin/permissions`, `/admin/activity`** (5 صفحات) محمية إضافيًا بـ`user:manage` (فحص مباشر داخل كل صفحة، لا Layout مشترَك — الأسباب في §5).
- **لا صفحة `/admin/login` موجودة إطلاقًا** (مُتحقَّق منه بالفحص) — لا خطر حلقة توجيه (Redirect Loop) لأن لا شيء يحمي نفسه.
- **كل الصفحات العامة (`/`, `/quran`, `/hadith`, `/articles`...) لم تُلمَس ولا تزال بلا أي حراسة** (خارج النطاق تمامًا، وصحيح — هذه صفحات عامة بالتصميم).

## 4. حماية Server Actions/Mutations (Layer B)

### 🔴 اكتشاف حاسم آخر أثناء الفحص

**بحث شامل عن كل `"use server"` في المشروع أعاد ملفًا واحدًا فقط:** `lib/actions/example.action.ts` (نموذج توضيحي معلَن صراحة كـ"ليس ميزة فعلية"). **بحث شامل عن `route.ts` تحت `app/api` أعاد ملفين فقط:** مسار NextAuth القياسي، و`/api/health`. **بحث عن أي `fetch` بطريقة `POST` من مكوّنات لوحة الإدارة أعاد نتيجة فارغة تمامًا.**

**الخلاصة الصريحة:** **لا يوجد حاليًا أي Server Action أو Route Handler أو نقطة API واحدة في المشروع كله تُنشئ أو تُعدِّل أو تحذف بيانات حقيقية.** كل أزرار "نشر"/"أرشفة"/"حفظ الإعدادات" في لوحة الإدارة (مُتحقَّق منه عبر كل تقارير Phase 11 السابقة) تُحدِّث حالة عميل محلية (`useState`) وتعرض إشعار Toast فقط — **لا طلب شبكة، لا تغيير بيانات حقيقي إطلاقًا.**

**ماذا يعني هذا لمتطلب "Layer B"؟** لا يوجد حاليًا **أي عملية حقيقية لحمايتها**. تنفيذ Phase 0.1 لهذا البند اقتصر على:
1. **إثبات الفحص السلبي أعلاه** (لا مفاجآت خفية).
2. **إرساء نمط إلزامي موثَّق** في `lib/actions/example.action.ts` نفسه — كل Server Action إداري حقيقي مستقبلي (سيُضاف بدءًا من Phase 12) **يجب** أن يستدعي `requirePermission()` كأول سطر في جسمه، وهذا موثَّق الآن كقاعدة صريحة داخل الملف المرجعي نفسه، لا فقط في هذا المستند.

**هذا ليس نقصًا في Phase 0.1** — هو انعكاس دقيق لواقع الكود؛ فرض حماية على عمليات غير موجودة كان سيعني كتابة كود وهمي.

## 5. نموذج التهديد (Threat Model)

| التهديد | الحالة قبل Phase 0.1 | الحالة بعدها |
|---|---|---|
| زائر مجهول يستعرض بيانات المستخدمين/الأدوار/الصلاحيات كاملة | 🔴 ممكن تمامًا | ✅ محجوب (توجيه لتسجيل الدخول) |
| زائر مجهول يستعرض إعدادات النظام (SMTP، AI، إلخ) | 🔴 ممكن تمامًا | ✅ محجوب |
| مستخدم عادي (MEMBER) يصل للوحة الإدارة كاملة | 🔴 ممكن (لا تمييز أدوار إطلاقًا) | ✅ محجوب (بوابة الصلاحية الأساسية) |
| معلّم (TEACHER) يصل لإدارة المستخدمين/الأدوار | 🔴 كان ممكنًا | ✅ محجوب (`user:manage` حكر على ADMIN) |
| تجاوز الحماية عبر استدعاء Server Action مباشرة | ⚠ غير قابل للتقييم — لا توجد عمليات حقيقية أصلاً | ⚠ نفس الحال، لكن النمط الإلزامي مُرسًى لأي عملية مستقبلية |
| قيم دور/صلاحية من العميل تُصدَّق دون تحقق خادمي | ✅ لم يحدث قط — كل الفحوصات هنا خادمية (Server Component)، لا أي اعتماد على مدخل عميل | ✅ لا تغيير، محافَظ عليه |

## 6. المخاطر المتبقية (صريحة، غير مُخفاة)

1. **🔴 لا يمكن لأي أحد تسجيل الدخول فعليًا** (§1) — يحتاج قرارًا ومزوِّد مصادقة حقيقي، خارج نطاق هذه الوحدة.
2. **🟡 `/admin/login` غير موجودة** — الاعتماد الحالي على صفحة NextAuth الافتراضية (`/api/auth/signin`)، والتي بلا مزوِّدين ستعرض قائمة فارغة عمليًا حتى تتم إضافة مزوِّد.
3. **🟡 Layer B نمط لا تطبيق فعلي** — لأن لا عمليات حقيقية موجودة بعد؛ يجب التحقق من الالتزام بالنمط الموثَّق فعليًا عند إضافة أول Server Action حقيقي في Phase 12.
4. **🟢 التحقق الحي (Runtime) لسلوك إعادة التوجيه لم يكتمل 100%** في بيئة هذه الجلسة تحديدًا (تفصيل السبب والبديل في `SECURITY_TEST_REPORT.md`) — قيد بيئي معروف (Prisma Client غير مُولَّد هنا)، لا خطأ في المنطق المُنفَّذ؛ يحتاج تأكيدًا نهائيًا على بيئة المستخدم الحقيقية.
